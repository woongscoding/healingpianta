# 기획 제안서

## 이 폴더의 목적

이 폴더는 바꾸고 싶은 기획을 제안서로 먼저 올려 합의하는 곳이다. 설계 기준인 [CLAUDE.md](../../CLAUDE.md)를 바로 고치지 않는다.

제안이 합의되어 CLAUDE.md에 반영되기 전까지는 지금의 CLAUDE.md가 계속 설계 기준이다.

## 제안서 목록

| 번호 | 제목 | 상태 | 작성일 |
|---|---|---|---|
| 001 | [가치 기반 미션과 활동 계획](001-values-and-planning.md) | 검토 중 | 2026-11-09 |
| 002 | [구조 검토](002-structure-review.md) | 검토 중 | 2026-11-09 |
| 003 | [기획 피드백과 추가 기능](003-product-feedback.md) | 검토 중 | 2026-11-09 |

상태 값:

- **검토 중:** 제안서가 올라왔고 아직 결정되지 않았다.
- **합의:** 저장소 주인이 받아들였다. CLAUDE.md에 반영할 대상이다.
- **보류:** 지금은 결정하지 않고 나중에 다시 본다.
- **반려:** 받아들이지 않기로 했다.

## 제안서 작성 형식

모든 제안서는 "한눈에 보기 → 상태 → 본문" 순서로 쓴다.

- **한눈에 보기:** 문제, 제안 요약, 저장소 주인이 결정해 주었으면 하는 것
- **상태:** 검토 중 / 합의 / 보류 / 반려 중 하나와 작성일
- **본문:** 아래 두 형식 중 하나

### 기능 하나를 제안할 때 (예: 001)

아래 항목을 이 순서로 쓴다.

1. **배경:** 왜 이 제안이 필요한지, 지금 기획에서 무엇이 비어 있거나 문제인지
2. **제안:** 무엇을 어떻게 바꾸자는 것인지
3. **사용자 흐름:** 사용자가 보게 되는 화면과 행동 순서
4. **데이터 구조 변경:** 추가하거나 바뀌는 콘텐츠 파일, Firestore 필드와 컬렉션
5. **CLAUDE.md 영향:** 합의되면 CLAUDE.md의 어느 절을 어떻게 고쳐야 하는지
6. **Phase 영향:** 어느 Phase에서 구현하는지
7. **원칙 충돌 검토:** CLAUDE.md 1절 절대 규칙과 부딪히는 점이 있는지, 있다면 어떻게 피하는지
8. **미결 사항:** 저장소 주인과 정해야 할 것, 전문가 검토가 필요한 것

### 여러 의견을 묶을 때 (예: 002, 003)

항목마다 "문제 / 제안 / 정할 것"으로 쓴다. 필요하면 "지금 상태"를 앞에 붙이거나, 항목 제목 옆에 [우선순위 / Phase / 전문가 검토]를 붙인다.

## 절차

1. 제안서를 이 폴더에 추가하는 PR을 올린다.
2. 저장소 주인이 검토한다.
3. 합의된 항목만 별도 PR로 CLAUDE.md에 반영한다.
4. 이 문서의 제안서 목록 표에서 상태를 갱신한다.
