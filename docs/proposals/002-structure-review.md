# 002 구조 검토

## 한눈에 보기

**문제**

- 기능이 아니라, 정해두지 않으면 사람마다 다르게 구현할 구조적 결정들이 아직 정해져 있지 않다.
- 판단 로직이 들어갈 자리, 데이터의 기준, 하루와 알림의 기준이 비어 있어 협업을 시작하면 중복과 충돌이 생긴다.

**제안**

- 6절의 판단 엔진 8개를 Firebase를 모르는 별도 계층으로 모아, Firebase 프로젝트 없이 지금 바로 개발·테스트한다.
- 원본 기록만 진짜 데이터로 두고, 기분 기록의 용도·하루 경계·알림 결정 위치를 하나로 정한다.
- Phase를 병렬 트랙으로 나눠 Firebase를 기다리는 동안에도 일을 진행한다.

**결정해 주셨으면 하는 것** (이 순서로)

1. 1번 판단 엔진 계층: 폴더 이름과 엔진별 입력·출력 형식
2. 2·3번 집계 값과 기분 기록: 값마다 누가 계산할지, 기분 기록별 용도
3. 4번 하루 경계: 새벽 5시로 할지
4. 5번 알림 결정 위치: 기기 한 곳에서 결정할지 (Phase 8 전)
5. 6번 앱 시작 관문 상태: 단계 정의와 저장 위치 (Phase 2 전)

## 1. 판단 엔진 계층 신설

- **지금 상태:** 폴더 구조(CLAUDE.md 3절)는 `core / data / features`만 있다.
- **문제:** 6절의 핵심 로직은 사실상 아래 판단 엔진 8개다. 들어갈 자리가 없어 화면 폴더마다 흩어지기 쉽다. 예를 들어 홈과 알림이 메시지 선택 로직을 각자 만드는 중복이 생긴다.

  | 엔진 | 입력 → 출력 |
  |---|---|
  | 메시지 선택 (6.2) | 상황, 시간, 에너지, 최근 기록 → 문구 하나 |
  | 행동 제안 (6.3) | 에너지, 사다리 진행, 최근 기분 변화, (001) 가치 → 미션 2개 |
  | 단계 결합 (6.1) | AI 결과, 날짜, 이전 단계 → 표시 단계 |
  | 알림 스케줄러 (6.4) | 설정, 오늘 보낸 수, 접속 기록 → 보낼지, 언제 |
  | 지지 모드 판정 (6.5) | 최근 기분, 키워드 → 진입·유지·해제 |
  | 주간 정원·누적 (6.6) | 기록 목록 → 돌본 날 수 |
  | 레벨 조건 (6.8) | 수확 횟수, 돌본 날 → 제안 여부 |
  | 알림 문구 학습 (6.9) | 카테고리별 알림 반응 기록 → 고를 카테고리 (Phase 14, 003 12번에서 보류를 제안함) |

- **제안:** `lib/domain/` 계층을 두고 엔진을 Firebase를 모르는 순수 로직으로 만든다. 화면은 데이터를 모아 엔진에 넘기고 결과만 받는다. Firebase 프로젝트가 없어도 엔진 개발과 테스트를 지금 시작할 수 있어, Phase 2가 막혀 있는 동안 협업자가 맡을 수 있다.

  ```
  features (화면) ──► domain (판단 엔진) ──► core (콘텐츠, 조사, 날짜)
        └──────────► data (Firestore 읽기/쓰기)
  ```

- **정할 것:** 폴더 이름(`domain` / `core/engine`), 엔진별 입력·출력 형식.

## 2. 집계 값의 소유자

- **지금 상태:** `careDaysTotal`, `supportMode`, `level`은 원본 기록에서 나오는 값인데, 보안 규칙상 앱이 `users/{uid}`에 직접 쓸 수 있다(`careDaysTotal`·`level`은 감소만 금지).
- **문제:** 기기 두 대(폰, 태블릿)에서 쓰면 서로 다른 값을 덮어쓸 수 있다. 사용자가 직접 쓸 수 있으니 지지 모드를 앱 밖에서 꺼버릴 수도 있다.
- **제안:** 원본 기록(체크인, 행동, 사진)만 진짜 데이터로 저장한다. 집계 값은 (a) 앱이 볼 때마다 원본에서 다시 계산하거나, (b) 원본이 쓰일 때 서버 함수가 계산해서 쓴다. 지지 모드처럼 안전과 관련된 값은 (b)가 맞지만, 위기 키워드 감지는 기기 안에서만 하므로(6.5) 키워드로 진입하는 경우만 앱이 쓰는 예외를 둔다.
- **정할 것:** 값마다 (a)/(b) 중 무엇으로 할지.
- **001과의 연결:** 001의 "자주 하는 시간"을 저장하지 않고 원본에서 계산하는 원칙, 두 기기에서 계획 알림이 두 번 울리는 문제와 연결된다.

## 3. 기분 기록이 세 군데에 있음

- **지금 상태:** `checkins/{날짜}.mood`(하루 기분), `actions.moodBefore / moodAfter`(행동 전후 기분), `photos.moodAtTime`(사진 찍을 때 기분).
- **문제:** 지지 모드의 "기분 1이 연속 3번 체크인"이 이 중 무엇을 세는지 정해져 있지 않다. 하루에 행동을 3번 하며 매번 1점을 찍으면 하루 만에 진입하는지, 3일이 걸리는지에 따라 의미가 완전히 달라진다. 주간 리포트의 기분 추이를 어디서 가져올지도 정해지지 않았다.
- **제안:** 용도를 못박는다. 예: 지지 모드·추이는 `checkins` 기준(서로 다른 날 기준), 행동 효과는 `actions` 기준, `photos.moodAtTime`은 앨범 표시용. 더 단순하게 하려면 기분 기록 컬렉션 하나로 합치고 출처 필드를 붙이는 방법도 있다.
- **정할 것:** 기분 기록별 용도, 지지 모드의 "연속"을 날짜 기준으로 셀지.

## 4. 하루 경계

- **지금 상태:** 체크인 키는 `yyyy-MM-dd`라 자정에 날짜가 바뀐다. 그런데 `messages.json`의 심야 시간대는 `23:00~04:59`다.
- **문제:** 새벽 1시 체크인은 "어젯밤"의 연장인데 "오늘"로 저장되고, 아침에 또 체크인하면 같은 날 두 번이 된다. 심야 사용자가 많은 앱이라 자주 생긴다.
- **제안:** 하루 경계를 새벽 5시로 정한다(시간대 정의와 맞춤). 날짜 계산은 `core/`의 시계 서비스 하나로 모아 모든 엔진이 같은 기준을 쓴다. 서버가 쓰는 `usage/{날짜}`도 같은 규칙과 사용자 시간대(`settings.timezone`)를 따른다.
- **정할 것:** 경계 시각, 시간대 기준.
- **001과의 연결:** 001의 "오늘의 계획"이 끝나는 시점이 이 결정을 따른다.

## 5. 알림 최종 결정 위치

- **지금 상태:** 정기 알림은 기기가 예약(`flutter_local_notifications`)하고, 판독 완료 같은 사건 알림은 서버가 FCM으로 보낸다. 하루 상한은 "새싹 이벤트 포함"이다(6.4).
- **문제:** 서버는 기기가 오늘 몇 개 보냈는지 모르니 상한을 넘길 수 있다.
- **제안:** 서버는 화면에 바로 뜨는 알림 대신 데이터 메시지만 보내고, 실제로 띄울지는 기기의 알림 엔진이 한 곳에서 결정한다. 상한·조용한 시간·지지 모드·(001) 계획 알림 우선순위가 모두 한 곳에 모인다.
- **정할 것:** 이 방식 채택 여부.
- **001과의 연결:** 001의 계획 알림 우선순위는 이 방식을 전제로 한다.

## 6. 앱 시작 관문 상태

- **지금 상태:** 로그인 → 연령 → 동의 → 고지문 → 온보딩 순서(7절)만 있고, 중간에 멈춘 사용자를 어떻게 처리할지 정의가 없다.
- **문제:** 화면마다 따로 확인하면 "동의는 했는데 온보딩 중에 앱을 끈 사람" 같은 경우가 새어 나온다.
- **제안:** "사용자 진행 단계"를 하나의 값으로 정의한다: `미로그인 → 연령 필요 → 동의 필요 → 고지 필요 → 온보딩 중 → 준비 완료`. 라우터는 이 값 하나만 보고 첫 화면을 정한다. 온보딩 중간 단계도 저장해 이어서 할 수 있게 한다.
- **정할 것:** 단계 정의, 저장 위치.

## 7. Remote Config 우선순위와 검증

- **지금 상태:** 위기 연락처, 지지 모드 기준, 쿠팡 링크를 Remote Config로 덮어쓰게 되어 있다.
- **문제:** 앱 내장 JSON과 원격 값 중 무엇이 우선인지, 원격 값이 잘못됐을 때(예: 109 번호 누락) 어떻게 하는지 정해지지 않았다.
- **제안:** 원격 값이 있으면 우선하되, 내장 값과 같은 검증기를 통과해야 하고, 실패하거나 못 받으면 내장 값을 쓴다. 위기 연락처는 틀리면 안 되는 값이라 특히 중요하다.
- **정할 것:** 이 규칙 채택 여부.

## 8. 서버 함수 목록

- **지금 상태:** 이름까지 정해진 함수는 `analyzeSprout` 하나이고, 계정 삭제(CLAUDE.md 4절)와 그룹 처리(`firestore.rules` 주석)는 서버 함수로 한다고만 적혀 있다.
- **문제:** 필요한 서버 함수가 CLAUDE.md 4절, firestore.rules 주석 등 여러 곳에 흩어져 있고 목록이 없어서, 백엔드를 맡은 사람이 해야 할 일의 범위를 파악하기 어렵다.
- **제안:** 설계상 필요한 함수 목록을 미리 만든다.
  - `analyzeSprout`: AI 판독
  - 계정 삭제: Firestore + Storage 전체 삭제 (앱 내 + 웹)
  - 그룹 생성·초대 코드 가입·탈퇴: 보안 규칙에서 클라이언트 쓰기를 막아뒀음
  - 집계 갱신: 2번을 서버 방식으로 정할 경우
  - 오래된 로그 정리: `messageLog`, `notifLog`는 14일분만 필요한데 끝없이 쌓임
  - 데이터 내보내기: JSON + 사진 zip 생성
- **정할 것:** 목록 확정, 우선순위.

## 9. 앱과 서버 사이 계약 문서

- **지금 상태:** 판독 결과 형식은 `functions/prompts/analyze_sprout.md` 안에, Firestore 문서 형식은 CLAUDE.md 4절에 글로만 있다.
- **문제:** 앱 담당과 서버 담당이 따로 일하면 필드 이름이 어긋나기 쉽다.
- **제안:** `docs/contracts/`에 Firestore 문서 형식과 판독 결과 스키마를 기계가 읽을 수 있는 형식으로 두고, 앱 모델·서버 검증·보안 규칙 테스트가 모두 그것을 기준으로 삼는다.
- **정할 것:** 형식(JSON Schema 등), 위치.

## 10. 보안 규칙 보완

- **지금 상태:** `users/{uid}` 문서를 본인이 자유롭게 고칠 수 있다(`careDaysTotal`·`level`의 감소 금지만 있음).
- **문제:** `consents`(동의 시각), `ageVerifiedAt`, `supportMode`를 클라이언트가 바꿀 수 있다. 동의 시각은 법적 기록이 되는 값이다.
- **제안:** 동의·연령 확인 시각은 한 번 쓰면 바꿀 수 없게 하거나 서버가 쓴다. `supportMode`는 2번 결정에 따른다.
- **정할 것:** 필드별 쓰기 권한.

## 11. 그 밖의 기술 이슈

- **지금 상태:** Firestore는 오프라인 캐시가 되지만 Storage 업로드는 아니다. PROGRESS.md에 "한국어 문장이 낱말 중간에서 줄바꿈됨"이 다음에 고칠 것으로 적혀 있다.
- **문제:** 오프라인에서 찍은 사진은 업로드에 실패한다. 줄바꿈은 Flutter에 CSS `word-break: keep-all` 같은 옵션이 없고, 큰 글씨가 원칙인 앱이라 자주 보인다.
- **제안:** 업로드 실패 시 대기열에 넣고 다시 보낸다. 어절 단위 줄바꿈 유틸리티를 직접 만든다.
- **정할 것:** 오프라인 업로드 대기열을 Phase 5에서 만들지, 어절 단위 줄바꿈을 Phase 3 홈 화면과 함께 처리할지.

## 12. 협업 방식

- **지금 상태:** Phase가 한 줄로 이어져 있고, CLAUDE.md 하나가 기획서·규칙·일정을 모두 겸한다. PR마다 자동으로 도는 CI가 없다. `tool/check.sh`는 개발 PC 경로(`C:\src\flutter`, `C:\src\jdk21`)가 있으면 그것을 쓰고, 다른 PC에서의 동작은 확인되지 않았다. 저장소는 공개(PROGRESS.md)다.
- **문제:** Phase를 순서대로만 하면 서로 기다린다. CLAUDE.md를 여럿이 동시에 고치면 충돌이 난다. 나중에 `google-services.json`을 공개 저장소에 올리면 API 키 사용 범위를 제한해야 한다.
- **제안:**
  - Phase 1 이후를 병렬 트랙으로 나눈다.

    | 트랙 | 내용 | Firebase 필요 |
    |---|---|---|
    | A. 콘텐츠·안전 | 문구, 전문가 검토, 지지 모드 기준 | 아니요 |
    | B. 판단 엔진 | 1번의 엔진 + 단위 테스트 | 아니요 (지금 시작 가능) |
    | C. 화면 | 온보딩, 홈, 행동 흐름 UI (가짜 데이터로 먼저) | 나중에 연결 |
    | D. 백엔드 | 함수, 규칙, 계약 문서 | 예 |
    | E. 새싹 모형 | CustomPainter + 골든 테스트 | 아니요 |

  - 문서를 나눈다: 절대 규칙은 CLAUDE.md에 남기고, 기능 명세는 영역별 문서, 결정 이유는 결정 기록(ADR), 제안은 `docs/proposals/`로.
  - `check.sh`가 다른 PC와 GitHub Actions에서도 돌게 하고 PR마다 자동 실행한다. 처음에는 에뮬레이터가 필요 없는 `check.sh --no-rules`부터 PR마다 돌리고, 보안 규칙 테스트는 그다음에 붙인다.
  - `google-services.json`을 올린다면 Firebase 콘솔에서 API 키 사용 범위(앱 패키지·인증서)를 제한한다.
- **정할 것:** 트랙별 담당자, 문서 분리 시기, CI 도입 시기, 협업 전에 저장소를 공개로 둘지.
